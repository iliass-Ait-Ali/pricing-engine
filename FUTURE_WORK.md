# FUTURE WORK — candidate directions after v1.0

**Nothing in this file is implemented.** v1.0.0 is frozen: its scientific
architecture, estimators, guardrails and decision policy are fixed. This
document exists so that ideas are recorded honestly *outside* the shipped
system, instead of being half-built inside it.

Read it together with [`KNOWN_LIMITATIONS.md`](KNOWN_LIMITATIONS.md), which
lists what v1.0 cannot do. **Freezing v1.0 solved none of those limitations.**

---

## The ordering rule

Two things must not be confused:

| category | what it needs | can it be done on this dataset? |
| --- | --- | --- |
| **Engineering work** | code, tests, time | yes |
| **Evidence work** | new data generated by an intervention | **no** |

Almost every interesting idea below is in the second category. The Dominick's
panel is observational: prices were set by a retailer for reasons that are
correlated with demand and are not recorded. No estimator, however
sophisticated, recovers a causal price effect from it. Adding methods that
*look* causal to observational data would make the project less honest, not
more advanced — which is why v1.0 stops where it does.

**The gate for everything in section 2 is a randomised pricing experiment.**
Its design already exists: [`docs/PRICING_EXPERIMENT.md`](docs/PRICING_EXPERIMENT.md).

## 1. Modelling and scope (engineering-first, still observational)

### 1.1 Cross-price elasticity and cannibalisation

The Phase M audit ranks this as the **most important remaining scientific gap**
(`reports/11`, §101 of the full report). Every elasticity in v1.0 is own-price,
so the category effect of re-pricing many substitutes at once is *not* the sum
of the per-product effects, and the engine cannot see that raising the price of
one cereal moves volume to another.

What it would take: a substitution structure (nested logit, a demand system, or
at minimum a cross-price matrix restricted to plausible pairs), estimated on the
same training weeks, plus a way to report its own uncertainty. It inherits every
identification problem of v1.0 and adds more parameters to a panel that already
struggles to identify 372 own-price coefficients (only 239 are usable — see
`reports/18`). Expect the shrinkage problem to get materially worse.

### 1.2 Category-level multi-product optimisation

Once cross-price effects exist, the optimisation problem changes from N
independent scalar problems to one constrained joint problem over a category:
maximise category gross profit subject to price-gap rules, own-brand versus
national-brand relationships, and a shelf-level change budget. This is a
genuinely different optimiser, not a bigger loop, and it should not be attempted
before 1.1 has credible estimates.

### 1.3 Distributional demand forecasts

v1.0 predicts a point. A quantile or full predictive distribution would let the
optimiser weigh downside risk instead of maximising an expectation, and would
let the risk layer stop being a heuristic (see 1.4).

### 1.4 A calibrated risk layer

The v1.0 risk score is an **asserted** heuristic: thresholds on observation
count, price variation, extrapolation distance and elasticity provenance. It is
transparent and auditable, but it is not calibrated confidence. Replacing it
would mean fitting the thresholds against realised out-of-sample error — which
requires the outcomes that only 2 or an experiment can supply.

*v1.1 note.* Two different things are mixed up in that sentence. Calibrating the
risk bands against **prediction error** does not need an experiment: the
154,899 out-of-time price-change episodes (`reports/16`) have realised demand,
so one could check whether HIGH-risk contexts really forecast worse.
Calibrating against **realised uplift** does need an experiment. The first is
a candidate for the next version; the second stays in section 2.
**Done:** `reports/26_RISK_CALIBRATION.md` runs that check. The bands separate
error only weakly; extrapolation distance is the factor that carries the
signal. Fitting new thresholds is left as an explicit policy change.

### 1.5 Guardrail design instead of guardrail dominance

`reports/11` shows the ±10% change cap binds first in 44.6% of contexts and that
only 2.9% of final recommendations come from an interior learned optimum. In
v1.0 that is a *finding*. A future version could make it a *design*: sweep the
cap against the width of the elasticity confidence interval, so the constraint
binds where the evidence is weak and relaxes where it is strong. That is a
policy change and must be justified as one — it is exactly the change that would
be tempting to make for the wrong reason (making the ML look more influential).

## 2. Evidence work (blocked until an experiment exists)

### 2.1 A randomised pricing experiment

The only route to a causal price effect and to *measured* rather than
model-internal uplift. Design, power calculation, randomisation unit,
contamination risks and stopping rules: `docs/PRICING_EXPERIMENT.md`. It would
also settle the open empirical question v1.0 has to hedge: whether the pooled
elasticity (−2.03) or the native ML response (−3.10) is closer to the truth.

### 2.2 Causal effect estimation — **only after 2.1**

With an intervention in hand, the usual estimators (difference-in-differences,
synthetic control, and yes, causal forests for heterogeneous effects) become
meaningful. Applied to the v1.0 observational panel they would produce
confident-looking numbers with no identification behind them. That is why none
of them is in v1.0, and why "add a causal forest" is not an upgrade path on its
own.

### 2.3 Contextual bandits / reinforcement learning — **only after 2.1 and a valid sequential setup**

An RL or bandit pricing agent needs three things this project does not have:

1. an **environment it can actually act in** (v1.0 recommends; it does not set
   prices);
2. **feedback from its own actions**, not from a retailer's historical policy —
   learning a policy offline from logged data with unknown propensities is
   off-policy evaluation, not RL, and it is exactly as circular as the v1.0
   backtest;
3. **safety machinery** appropriate to real prices: exploration budgets,
   per-series risk limits, and a way to stop.

Until a sequential experimental setup exists, a bandit here would be a
simulation of a bandit scored by the same model that proposes the actions.

### 2.4 Realised uplift measurement

Only meaningful downstream of 2.1. Until then, every uplift number in this
project is and must stay labelled **model-internal estimated**.

## 3. Product and operations (no new science)

* **Staff the `REVIEW_REQUIRED` queue.** 10.4% of contexts (1,353 of 13,964 in
  the full decision week) escalate to a human. v1.0 produces the queue and the
  audit trail; it does not provide a review UI, an approval workflow or an
  SLA. **[Engineering done, `reports/22`]:** `scripts/review.py` (a
  non-interactive CLI) and a dashboard "Review queue" page now let a human
  move a recommendation through GENERATED → REVIEWED → APPROVED/REJECTED →
  PUBLISHED. No real staffing, SLA, or notification path is claimed - this is
  the tool a reviewer would use, not the reviewer.
* **Recommendation lifecycle in a real store.** The audit log models
  GENERATED → REVIEWED → APPROVED/REJECTED → PUBLISHED, but nothing consumes it.
  **[Engineering done, `reports/22`]:** the state machine above is now
  enforced (illegal transitions raise), recorded in an append-only
  `recommendation_transitions.csv` that never rewrites `recommendation_log.csv`.
  Nothing outside this repository still consumes it.
* **A real cost feed.** The AAC proxy is an average acquisition cost implied by
  the accounting margin; it lags replacement cost. Temporal availability is
  proven (`reports/10`), economic correctness is not. **Not attempted** - no
  external cost data source exists for this project.
* **Online monitoring.** v1.0's monitoring is offline: drift, schema and
  performance checks run on demand, with no metric store and no alerting.
  **[Engineering done, `reports/22`]:** every `scripts/monitor.py` run now
  appends to `artifacts/metrics/monitoring_history.jsonl` and is checked
  against config-driven local thresholds (`evaluate_alerts`), exiting
  non-zero on a breach. This is a flat append-only file and a local
  comparison, not a metric-store database or a paging integration; the
  thresholds are not business-calibrated.
* **Run the GitHub-hosted CI.** The workflow exists and every step has been
  reproduced locally, but it has never executed on GitHub because no remote is
  configured. **Not attempted in Phase O** - out of scope by explicit user
  decision (no remote/push). **Done on 2026-10-05:** published, first hosted
  run green.
* **Scale testing.** The batch path was vectorised in v1.0 and measured once, on
  one machine: 3,000 contexts, 122.0 s → 2.4 s. That is a local measurement, not
  a scalability claim; a real claim needs a fixed harness across catalogue sizes
  and hardware. **[Engineering done, `reports/22`]:** `scripts/benchmark_scale.py`
  sweeps `optimize_price_batch` across context counts up to 30,000+ on this
  one machine. Sizes above the 3,000-context real sample are that sample
  **replicated**, not independent catalogue growth, and no other-hardware
  claim is made.

## 4. What will not be added

For the avoidance of doubt, and because these are the usual suggestions:

* **Deep learning for demand.** The binding constraint is identification and
  data quality, not model capacity. A ridge log-log model beats the best naive
  baseline by 37.7% relative WAPE; the guardrails, not the model class, decide
  the price 97% of the time (`reports/11`, `reports/12`).
* **More forecasting models.** The comparison already spans four naive
  baselines, a linear log-log model and gradient boosting, on a strict
  chronological split. Adding a seventh changes nothing about the finding.
* **Causal-looking methods on observational data** — see 2.2.
* **Anything that loosens a guardrail to make the model appear more
  influential.** The 2.9% attribution result stands as measured.
